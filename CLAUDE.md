# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

RobocodeJs is a browser-based programming game where users write JavaScript "bots" (tank AIs) that battle in teams in a shared arena. It is a monorepo of two app packages, a VS Code extension, and a tiny root dev proxy:

- `index.js` — root dev reverse proxy (port 5000). Routes `/api` and `/health` → `:8080` (server), everything else → `:3000` (ui). This is the port forwarded by `.devcontainer`.
- `server/` — Express + TypeScript API and the game simulation engine (port 8080). Package `@robocodejs/server`.
- `ui/` — Vite + React + TypeScript front end (port 3000). Renders the arena as SVG and the bot code editor.
- `vscode/` — the VS Code extension (prototype, GitHub #438): an **MCP client** of `POST /api/mcp`, signing in via the server's OAuth 2.1 flow with a loopback callback published through `vscode.env.asExternalUri` (a `vscode://` redirect fails in browser Codespaces) (the bearer token is only accepted on `/api/mcp`, so the extension never touches the cookie-authed REST API). Live bot logs come from `GET /api/mcp/arenas/:arenaId/logs` (`mcpAuth` + ownership, SSE, sharing `util/logStream.ts` with the cookie REST route): the one bearer-authed route outside `POST /api/mcp`, kept under the MCP resource path so the token is never honoured on the REST API. Runtime crashes come from `recent_faults`, triggered by ERROR lines on that stream plus a slow poll, and the status bar polls `match_status` (mind the 60/min per-user MCP budget when adding polling). The arena panel frames the public `/watch/:arenaId` page in a webview (one renderer, no second copy of the client physics); `/watch/*` is the only path whose `frame-ancestors` lists VS Code's webview and workbench origins (`middleware/securityHeaders.ts`), and general embedding stays off (#126). Apps are edited as real files in extension storage (VS Code's TS service only gives full IntelliSense to `file:` documents) next to a copy of `robocode.d.ts`, and each save is pushed with `set_app_source`. It relies on the shape of `check_app_source` messages (`(line L, char C)`, with the `wrapSource` prefix offset on line 1) and on `get_app_source`'s empty-app sentence — see `vscode/src/problems.ts` / `source.ts` when changing either. Not deployed by the pipeline; packaged with `npm run package` (`.vsix`). `vscode/README.md` **is the Marketplace listing** (packed into the `.vsix`), so keep it strictly user-facing; developer notes go in `vscode/DEVELOPMENT.md`, which `.vscodeignore` keeps out of the package.

## Commands

There is no root-level install/build; work inside `server/` and `ui/` separately.

```bash
# Local dev (run all three in separate terminals)
node index.js                 # root proxy on :5000
(cd server && npm run dev)    # builds, then tsc --watch + node --watch on :8080
(cd ui && npm run dev)        # Vite dev server on :3000 (npm start is an alias)

# Build (mirrors buildspec.yaml)
(cd ui && npm run build)      # tsc --noEmit type-check, then vite build → server/dist/public
(cd server && npm run build)  # tsc -> server/dist

# Lint / format (per package; both use prettier + eslint with --fix)
(cd server && npm run lint)
(cd ui && npm run lint)
```

Both packages use **Vitest** (`npm test` runs `vitest run`, `npm run test:watch` for watch mode). Tests live in each package's `test/` directory (outside `src`, so they're excluded from the `tsc` build). Server coverage spans the simulation physics (`simulation.test.ts`), tick-driven timers (`scheduleFactory.test.ts`), the `Tank`/`Turret`/`Radar` classes (`tankTypes.test.ts`), the API endpoints with auth/ownership (`api.test.ts`, `auth.test.ts`, `session.test.ts`), the Postgres services (`services.test.ts`), name generation (`nameFactory.test.ts`), **real-isolate** sandbox integration (`compiler.test.ts`), and **full sandbox+simulation** integration (`simulationIntegration.test.ts` — a real bot compiled into a real isolate and driven through `Simulation.run` tick by tick, asserting tank state); the UI covers the SSE reducer (`arenaReducer.test.ts`), shared geometry (`geometry.test.ts`), and client-side interpolation (`simulate.test.ts`). Three patterns recur: `Simulation.run` is driven with lightweight mock tanks (it only invokes `tank.handlers[...]` and mutates plain fields, so no isolates are needed); `compiler.test.ts` spins up a real `isolated-vm` isolate to lock the bot-facing contract; and `simulationIntegration.test.ts` combines both — manually advancing ticks with a short settle for the async handlers. Bot commands are async, but their side effects (e.g. `speedTarget`) land synchronously, then `Simulation.run` applies physics synchronously over ticks. DB-/isolate-coupled modules `vi.mock('../src/util/db', ...)` (or mock the relevant services) at the top of the file.

`ui build` writes directly into `server/dist/public` (`build.outDir` in `ui/vite.config.ts`, with `emptyOutDir` clearing it first), so the server can serve the built UI as static files in production. Deployment is AWS CodePipeline (`RobocodeJs`, a **V2** pipeline) → CodeBuild (`buildspec.yaml`) → Elastic Beanstalk (`server/.ebextensions`). The pipeline is **tag-triggered**: its only trigger is a push filter on Git tags matching `v*`, so **merging to `main` does NOT deploy** — a prod deploy happens only when you push a `vX.Y.Z` release tag (see the release steps below). This decouples integration from release and gives exactly one deploy per tagged version.

**CI** runs on every PR/push (`.github/workflows/ci.yml`): per package, `npm ci` → lint → build (`tsc`) → test → dependency-vulnerability gate (`scripts/audit-check.cjs`, run from each package dir — a thin wrapper over `npm audit --json` that keeps the old `--audit-level=high` severity gate but adds a short, justified allowlist for non-applicable/unfixable advisories; see Accepted risks below) (the native `isolated-vm` build needs Node 24 + `gcc`/`gcc-c++`, provided on the runner). `.github/dependabot.yml` opens weekly npm + github-actions update PRs.

To cut a release, run `npm run release` from the **root**. It builds `ui` + `server` (a pre-release type-check gate), then bumps the version (`npm version patch --no-git-tag-version`, no npm commit/tag), regenerates `npm-shrinkwrap.json`, and sets the **VS Code extension to the same version** (`scripts/sync-vscode-version.cjs`). **Always commit the resulting version bump (`server/package.json` + `server/npm-shrinkwrap.json` + `vscode/package.json` + `vscode/package-lock.json`) and push it to `main`** with a `build: bump server to vX.Y.Z (from npm run release)` message — this is the established convention, and it is now also the **release trigger**. **Pushing the tag is what deploys** — the V2 pipeline's `v*` tag trigger runs Source→Build→Deploy against the tagged commit, so the bump commit reaching `main` on its own does nothing until the tag is pushed. (This replaced the old branch-push trigger, under which the bump commit _and_ every feature merge each deployed — two deploys per release, plus a prod deploy on every incidental merge.) Bump commits through **v1.2.68** were backfilled with tags; every release from v1.2.68 on is tagged.

**The tag is pushed for you, off-hours.** `.github/workflows/release-tag.yml` runs at **07:00 UTC Mon–Fri** (3am EDT / 2am EST): it reads the version from `server/package.json` on `main`, and if `vX.Y.Z` is not yet tagged it finds that version's `build: bump server to vX.Y.Z` commit, checks CI concluded `success` on it, and pushes an annotated `vX.Y.Z` tag against **that commit** (not main's HEAD — so anything merged after the bump waits for the next release, and `git log <prev-tag>..<tag>` stays an honest notes range). So the sequence is: merge the bump commit whenever, and the deploy lands in the next off-hours window. **To hold a release, hold the bump commit.** The job refuses to guess — a version with no matching bump commit, or a bump commit that doesn't actually carry that version, fails the run loudly rather than tagging something arbitrary; red CI on the release commit likewise fails rather than deploying it. `workflow_dispatch` runs it on demand (with a `dry_run` input) when you want to ship immediately, and tagging by hand still works — the job simply finds the tag already present and no-ops. Note the tag is pushed with `GITHUB_TOKEN` and so does not trigger other Actions workflows; CodePipeline is unaffected because it watches the CodeStar connection, which sees the underlying git push.

**The extension shares the release version.** `vscode/` carries the server's version (CI's `vscode/test/version.test.ts` fails if they drift), so tag `vX.Y.Z` describes both the server and the extension built from it, and an extension version names the server it needs (extension X.Y.Z expects server ≥ X.Y.Z). Publish the extension (`cd vscode && npm run package`, then `vsce publish`) from a released tag, after its deploy, and only when it changed; releases that don't touch `vscode/` simply aren't published. An extension-only fix therefore ships through a normal release. Never hand-edit either version.

**Every release gets GitHub release notes.** The tag list is the deploy history, so a bare tag is a gap in it. Once the tag exists — usually the morning after the scheduled job pushed it — publish a Release describing what changed:

```bash
gh release create vX.Y.Z --verify-tag --title "vX.Y.Z" --notes-file <notes.md>
```

Creating a Release against an **existing** tag fires a `release` event, not a tag `push`, so it does **not** re-trigger the deploy pipeline — notes can be written or revised at any time, including well after the deploy. Source the notes from `git log --no-merges <prev-tag>..<tag>`; reach for `git show <sha>` or `gh pr view <n>` when a subject is too terse to explain what actually changed. House style:

- Open with **one headline sentence** naming the release's theme, then grouped bullets under bold headings — **Features** / **Fixes** / **Build & Tests** / **Docs**. Omit any group with no content.
- Add a **Breaking** group **first** whenever the release changes a bot-facing or MCP-client contract (a renamed tool, a changed response key, a removed capability). Consistency matters here: these are the bullets readers most need to find.
- Rewrite commit subjects into **user-facing language** and drop the `feat(server):` prefixes. Consolidate related commits into one bullet; if a change landed in several passes, describe the **shipped end state**, not the journey.
- **Omit** the `build: bump server to vX.Y.Z` commit — release plumbing, not a change. Don't pad a small release: a headline plus one bullet is a correct note.
- Notes are **historical**. Describe what that tag shipped, using the names it shipped with — don't retro-correct for a tool later renamed or removed.
- **Never invent.** If a commit's intent isn't recoverable from its message or diff, leave it out rather than guess. Terminology per the Conventions below: "app" = the code, "bot" = a live instance.
- No emoji, no AI-attribution footer.

v1.2.46–v1.2.91 were backfilled on 2026-07-16 and are the style reference — v1.2.90 is a typical small release, v1.2.46 the outlier (a 104-commit narrative spanning the 2023→2026 dormancy gap). The nine 2023 tags (v1.0.0–v1.2.45) are **deliberately left bare**: their commit subjects (`refactor`, `updates`, `db integraiton`) are too thin to summarize honestly.

`npm run release` deliberately does **not** build a deploy zip — the pipeline rebuilds from source (`buildspec.yaml`), so nothing consumes a local zip. The separate `npm run bundle` (root: build + `server` zip, no version bump) is a **break-glass fallback** that produces `server/robocodejs-vX.Y.Z.zip` for a **manual EB-console upload** — use it only if the pipeline is down (e.g. a broken CodeBuild). The zip is git-ignored.

## Runtime requirements

The server requires `node >=24`, pinned by the native `isolated-vm` dependency: isolated-vm 5.x requires Node ≥18, 6.x ≥22, and 7.x ≥26 — so the isolated-vm major and the Node major must move together. We run Node 24 (LTS) with isolated-vm 6.x; bumping to isolated-vm 7.x would require Node ≥26. The Node major is fixed at each layer that actually runs the code — the dev container (`.devcontainer/devcontainer.json`), CI (`nodejs: 24` in `buildspec.yaml`), and the Elastic Beanstalk **platform branch** (`Node.js 24 running on Amazon Linux 2023`) — **not** by a `server/package.json` `engines.node` field: the EB AL2023 Node platform selects Node from its branch and ignores `engines.node`, emitting a "used the platform default instead of your package.json" deploy warning whenever it's present, so we deliberately omit it (AWS's own guidance). `engines.npm` is kept. If `isolated-vm` fails to build or load, a Node/isolated-vm version mismatch is the first thing to check; the native build needs `gcc`/`gcc-c++` (provided in the container and in `server/.ebextensions/options.config` for Elastic Beanstalk).

The server needs Postgres via `RDS_*` env vars (`RDS_USERNAME`, `RDS_HOSTNAME`, `RDS_DB_NAME`, `RDS_PASSWORD`, `RDS_PORT`); see `server/src/util/db.ts`. The pool is sized explicitly rather than left at pg's defaults (GitHub #411): `PG_POOL_MAX` (default `20` per instance, sized so 4 instances still fit under the `db.t3.micro`'s ~112 `max_connections`), `PG_POOL_CONNECT_TIMEOUT_MS` (default `5000`, so an exhausted pool fails fast instead of queueing forever), and `PG_POOL_IDLE_TIMEOUT_MS` (default `30000`). Connect timeouts are logged as `event=db.error`, which feeds the `robocodejs-db-error` alarm. Services create their own tables lazily with `CREATE TABLE IF NOT EXISTS` at import time.

**Local-dev mode** (`util/devMode.ts`, `isLocalDev`): when `NODE_ENV` is neither `production` nor `test` **and** `RDS_HOSTNAME` is unset, the server runs with an in-memory Postgres (`pg-mem`, a devDependency `require`d lazily in `db.ts`) and an **auth bypass** that attaches a fixed "Local Dev" user (`ensureDevUser` in `middleware/auth.ts`) — no real database or Google sign-in needed. New users (including the dev user) are bootstrapped with starter bots and a running arena by `UserService.create`. The mode is force-disabled in production (re-checked at the auth-bypass site) and in the test suite. Don't rely on it serving requests with real persistence — data resets each restart.

## Architecture

### Bot sandboxing (the core of the system)

User bot code is untrusted JavaScript run in `isolated-vm` isolates — this is the central design constraint.

- An **`Environment`** (`server/src/types/environment.ts`) is one arena instance held in memory. `EnvironmentService` keeps a `Map<arenaId, Environment>` and disposes environments 30 minutes after they stop (isolate cleanup).
- Each **`Process`** = one app (bot program) in an arena, owns one `ivm.Isolate` sandbox (8 MB limit) and **5 `Tank` instances** that all share that isolate.
- `util/compiler.ts` is where the bot-facing API is built: for every method it sets a native `_bot_*` function on the isolate global, then compiles a thin JS wrapper (`bot.turn`, `bot.radar.scan`, `bot.turret.fire`, `arena`, `clock`, `console`, `setInterval/setTimeout`, `Event`, etc.) that bridges to it. **The `ivm` module is never exposed to bot code** (per isolated-vm's security guidance): all `Callback`/`Reference`/`ExternalCopy` objects are built host-side. Async bot APIs are Promises parked in an isolate-side `__pending` table and settled by the host via a captured `__settle` reference; events and timers use the same dispatch-table pattern (`__dispatch`/`__runTimer`), with the host pinning those references at init so a bot can't reassign them. Bot code (script load, event handlers, timer callbacks) runs via isolated-vm's **async `run`/`apply`** — on the thread pool, off the main event loop — each bounded by `SANDBOX_TIMEOUT_MS` (default 5s); a timeout or throw sets `tank.appCrashed` and Simulation kills the bot. `Date` is deliberately set to `undefined` to keep bots deterministic — bots use `clock.getTime()`.
- **Adding or changing an exposed `_bot_*` function is a security-sensitive edit — the copy boundary is the sandbox boundary.** Every native function installed on the isolate global must hand back only **copied plain data** (`new ivm.ExternalCopy(...)` for getters, `ExternalCopy(...).copyInto()` when settling), never a **live host object, function, or `ivm` `Reference`**: a returned host reference (or a plain object still carrying host-backed methods) is a path off the sandbox. Same rule for the dispatch machinery — new host-driven entry points (`__dispatch`/`__settle`/`__runTimer`-style) must be **pinned as References at init, before any bot code runs**, so a bot reassigning the global can't hijack them. The escape-relevant guarantees (no Node/host global — incl. `ivm` — reachable in bot scope, `Date === undefined`, seeded in-isolate `Math.random`, and un-hijackable dispatch/settle) are locked by the **"sandbox security contract"** tests in `server/test/compiler.test.ts`; extend them whenever you add a capability, and treat a failure there as a security bug, not a flaky test.
- The bot API surface lives entirely in `compiler.ts`; bot-author documentation is in `ui/public/docs/*.md` and example bots in `ui/public/samples/*.js`.

### Simulation loop

- `Environment.resume()` runs a **self-scheduling async loop** (`runLoop` → `tick` → `drainBotWork`), _not_ a fixed `setInterval`: each tick runs the physics, then **awaits** that tick's bot work (handlers, timers, command settlements) before the next tick begins — the guarantee that makes the sim deterministic at any speed. Cadence is set by `setSpeed` (a multiplier; `1` = the default ~10 ticks/s, `0`/`"max"` = unbounded). `clock.time` increments by 1 per tick and **resets to 0 on `restart()`** (so a new match never inherits the prior match's sudden-death state).
- `util/simulation.ts` (`Simulation.run`) is the physics/interaction engine: runs START/TICK handlers, fires timers (`scheduleFactory.timerTick`), moves tanks, detects collisions and bullet hits, applies damage, and emits events. After `SUDDEN_DEATH_TIME` ticks it decays health to force a winner. A crashed bot (`tank.appCrashed`) is killed; a tank's death tick is recorded on `Tank.eliminatedAt` for the match summary.
- **Idle arenas pause themselves.** Nothing else pauses a running arena (the 30-min GC only collects arenas that are already stopped), so without this every arena anyone resumed would tick, isolates and all, until the next deploy. `EnvironmentService.pauseIdle` (on the 10 s GC interval) pauses a running arena with no `event`/`log` SSE listener and no `get()` for `ARENA_IDLE_PAUSE_MS` (default 5 min, `0` disables), marking it `idlePaused`; the next `environmentService.get()` — status poll, SSE connect, compile, any MCP tool — wakes it before the caller sees it. A user pause clears the flag, so a user-paused arena is never woken. An idle-paused arena that the 30-min GC then disposes is remembered by id (`wakeOnLoad`) and rebuilt **running** (as a fresh match) on next access. A driven `run_match` is never idle-paused. Measured 2026-10-30: one 20-bot arena costs ~4% of a vCPU, so this is what keeps CPU tracking players online. `getByArenaId` deliberately does **not** wake.
- Timers are **monkey-patched** (`util/scheduleFactory.ts`): bot `setInterval`/`setTimeout` are driven by simulation ticks, not real time, so the game can pause/resume/stop them.
- **Determinism:** each `Environment` has a seeded PRNG (`util/random.ts`, mulberry32) driving tank placement/orientation, each bot's turret/radar starting angle and in-isolate `Math.random`, and each bot's sandbox-observable id (`bot.getId()`, a scanned contact's id — seed-derived via `deterministicBotId`, folding in the stable arena id so same-seed arenas stay distinct) — a fixed seed (`setSeed`, `POST .../arena/seed`, `set_arena_seed`) reproduces a match. Every seed-derived per-bot value is drawn **synchronously in `restart()`** (fixed team/slot order) _before_ the async per-process app fetches, so reproducibility can't hinge on which app row's `appService.get` resolves first. Combined with the tick-driven loop, accelerated headless runs are repeatable.

### Server <-> UI communication

- REST endpoints live in `server/src/api/*.ts` (`app`, `arena`, `user`, `demo`, `help`, `health`, `session`, `token`, `mcp`), wired up in `index.ts`. Most are namespaced under `/api/user/:userId/...`. Two shared builders back both REST and MCP: `util/arenaStatus.ts` (`buildArenaStatus` — the live per-tank snapshot, `GET .../arena`) and `util/matchSummary.ts` (`buildMatchSummary` — the outcome-oriented leaderboard/winner/elimination view, `GET .../arena/summary`).
- Live arena state streams to the browser via **Server-Sent Events**: `GET /api/user/:userId/arena/events` (game events) and `/arena/logs` (bot console output). The `Environment` is an `EventEmitter`; adding an `event` listener replays current state (place app/tank events) so a new client can bootstrap.
- The UI (`ui/src/App.tsx`) consumes the SSE stream and applies a large per-event-type reducer to its arena state. Between server ticks it runs its **own** client-side physics (`ui/src/util/simulate.ts`, a partial mirror of the server's `simulation.ts`) to interpolate smooth motion. Keep these two simulations consistent when changing movement math.
- **Theme:** a whole-app light/dark theme lives in `ui/src/util/theme.ts` (a `useSyncExternalStore` store — header toggle, persisted to `localStorage`, OS-default). The boolean drives a `body.dark` CSS-variable theme (`ui/src/index.css`), the Ace editor theme, and the arena SVG's night-mode tint.

### Auth & access control

`server/src/middleware/auth.ts` verifies a Google OAuth id token (checking its **audience** against `GOOGLE_CLIENT_ID`, which must match the client id the UI signs in with) stored in the `auth` cookie. The cookie is set **server-side and HttpOnly** by `POST /api/session` (the UI posts the Google credential there; `DELETE /api/session` logs out) — see `server/src/api/session.ts`. A user record is auto-created on first login (rejected if `email_verified` is false). Both `/api/user` and `POST /api/mcp` are hard-gated by `auth(true)` — the latter resolves the acting user from a **bearer API token** (`api/token.ts`, stored only as a sha256 hash). Ownership is enforced by two middlewares (`middleware/resource.ts`): `requireOwner` (the actor owns the `:userId`/arena) and `requireAppOwner` (the confidential/destructive app routes — source read/write, delete, compile, reboot — the A01 IDOR fix). Metadata reads and add-by-reference stay open by design (spectating / share-links).

### AI integration (MCP)

`server/src/api/mcp.ts` is an in-process **Model Context Protocol** server at `POST /api/mcp` (Streamable HTTP, stateless, bearer-token auth) exposing ~28 tools (bot CRUD + `check_app_source`/`format_app_source`/compile/reboot; arena create/delete/control incl. `set_arena_speed`/`set_arena_seed`; `arena_status`, `match_summary`/`match_status`; `platform_status`; `recent_logs`/`recent_faults`; the global `leaderboard`), **resources** (bot docs, `robocode.d.ts`, samples, error codes), and **prompts** (`write_app`, `debug_app`, `play_match`). Own-resource tools address apps/arenas by `appId`/`arenaId` (not a bare `id`), and pure control actions return a verb-specific flag (`paused`/`resumed`/`restarted`/`updated`/…). Almost every tool acts only on the token owner's own resources (`ownedApp`/`ownedArena` mirror the REST ownership checks) — keep the MCP caps in sync with the REST caps by hand; the `leaderboard` tool is the one deliberately global (public ranking data). The three **read-only arena view** tools (`arena_status`/`match_summary`/`match_status`) resolve by `readableArena` instead: given any `arenaId` they spectate that arena without an ownership check (the MCP counterpart of the public REST `GET /api/arena/:arenaId` + the `/watch` share link, GitHub #135), while every write/control arena tool (pause/resume/restart/speed/seed, roster edits, `run_match`) and `recent_logs`/`recent_faults` stay `ownedArena`-gated. User-facing setup guide at `/mcp` (`ui/public/docs/mcp.md`).

### Global bot ladder (GitHub #151)

A background matchmaking system that gives every eligible app a persistent **Elo rating**, separate from user arenas. `services/LadderService.ts` runs a self-scheduling loop: `pickPair` (eligibility via `AppService.getLadderCandidates` — non-deleted/non-broken, non-empty, app + owner active within 3 months, minus untouched starters from `util/starterBots.ts`; biased toward fewest-games + nearest-rating, different owner) → `runOneMatch` (an **ephemeral, non-persisted** `Environment` with two `Process`es, random seed, run to `deriveMatch().decided` via the shared `util/runMatch.ts` `runMatchToDecision` — also used by the MCP `run_match`) → `util/elo.ts` `updateRatings` (placement K-boost) persisted on the `app` row (`rating`/`ratingGames`/`ratingWins`/`broken`), match logged to `ranked_match` (`RankedMatchService`). The rating rides the app's **current** source (never reset on edit — editing clears `broken`), so effectiveness drifts the score over ~20–40 games. The loop is **opt-in** (`LADDER_ENABLED=true`, never under test), conservative by default (1 worker, `LADDER_*` env knobs), and **load-gated** off `EnvironmentService.metrics().isolates` so ranked matches yield to live players on the small prod box. Ranked matches are also **tick-rate-capped** rather than run unbounded: `LADDER_MATCH_SPEED` (default `20`) is passed to `runMatchToDecision` as its `speed`, so a background match paces at ~5 ms/tick instead of pinning a core at 100% (the MCP `run_match` tool still passes no speed → `0`/unbounded, so an interactive match decides as fast as possible). Because a bounded speed lengthens a match in wall-clock — a full sudden-death match (`SUDDEN_DEATH_TIME`=7500 ticks) takes ~`7500/(10·speed)` s, ~37.5 s at the default — keep `LADDER_MATCH_TIMEOUT_MS` (default 60 s) above that or slow matches time out unrated; `LADDER_MATCH_SPEED=0` restores the old unbounded behaviour.

**Multiple runners are safe** (GitHub #409) — more than one worker (`LADDER_CONCURRENCY`) and more than one instance (ASG scale-out, or old + new overlapping during an Immutable deploy) can run the ladder at once. Three guards make that true: (1) **cross-instance claims** — `runOneMatch` claims both apps in the `ladder_claim` table (`services/LadderClaimService.ts`) before starting, all-or-nothing, and releases them at teardown; the in-memory `inFlight` Set only covers one process. A claim is a **lease** (`claimedAt`, TTL `2 × LADDER_MATCH_TIMEOUT_MS + 60 s`), so one stranded by a crashed or redeployed instance expires instead of benching the app; `pickPair` skips live-claimed apps up front. Success is read back by a per-attempt token rather than trusted from `INSERT … RETURNING`, because pg-mem returns conflicting rows from `RETURNING` under `ON CONFLICT DO NOTHING`. (2) **Incremental ratings** — `App.applyRatingResult` writes `rating = rating + delta`, `ratingGames + 1`, `ratingWins + won`, never absolute values, so two results for the same app that land during one ~40 s match both count instead of the later overwriting the earlier. (3) **Cap re-checked under the claim** — `pickPair`'s pair-cap check is check-then-act, so `runOneMatch` re-checks saturation after claiming and returns `reason: 'saturated'` if another runner filled the pair meanwhile. Keep all three when changing the match path.

**Prod pacing is set in `server/.ebextensions/options.config`, not left at the defaults** (measured 2026-10-10): at the default 3 s interval the loop ran a ~100% duty cycle — 5,589 matches in 24 h — which held the EC2 box at 38–42% CPU with `CPUCreditBalance` pinned at 0 and squeezed the 1 GB `db.t3.micro` (`FreeableMemory` falling ~19 MB/month until the `robocodejs-rds-freeable-memory` alarm tripped on 2026-10-09). Worse, 20% of those matches finished `decided:false` because the box was too contended to hold the ~37.5 s sudden-death pace inside the 60 s timeout, so **49% of the loop's wall clock produced no rating at all**. Prod therefore pins `LADDER_MATCH_INTERVAL_MS=30000` and `LADDER_MATCH_TIMEOUT_MS=120000`. Throttling costs nothing: the top apps already carry 21,000+ games against the ~20–40 a rating needs to stabilise.

**A pairing stops replaying once it has nothing left to prove.** `pickPair` refuses a pair that has already met `LADDER_PAIR_MATCH_CAP` times (default `10`; `0` restores play-forever) since the **later** of the two apps' last edits. The pool is far smaller than the match volume suggests — 12 eligible apps in prod on 2026-10-10, so only **66 distinct pairings**, each of which the loop was replaying **~85 times a day forever** (the top apps' 21,743 games are ~1,800 matches against each of 11 opponents, against the ~20–40 a rating needs to settle). The cap is sized for **sampling, not convergence**: spawn placement is random per seed and outcome-deciding, so one match is noise and ~10 seeds is a reasonable read on a pairing. Once every pairing is saturated the loop idles on `idleMs` until someone edits a bot, so a quiet ladder is the expected steady state, not a fault. Two implementation notes: an exhausted **anchor** is not an exhausted **pool** (one app can be capped against everyone while other pairings are open, so `pickPair` tries further anchors), and saturation is measured with **one query per anchor** (`matchesForApp`) folded per opponent in JS, because each opponent's cutoff depends on its own edit time — no single portable aggregate expresses that, and pg-mem has neither window functions nor a working `= ANY($1)`.

This makes `app.updatedTimestamp` load-bearing as the "**this app's code changed**" signal, which is why `App.setName` no-ops for an unchanged name: every bot re-asserts its name via `bot.setName` on each script load and the ladder boots 10 bots per match, so writing there would reset saturation continuously. The same column drives `getLadderCandidates`' 3-month activity gate.

`ranked_match` is therefore **control state, not an archive** — the rows that exist for a pair _are_ its head-to-head record between both apps' current versions, and their count _is_ its saturation. Two retention mechanisms, with different jobs: `runOneMatch` retires a pairing's **pre-edit** rows right after recording (so the live rule and the control rule read the same rows), and the hourly sweep (`maybePruneHistory` → `deleteOlderThan`, `LADDER_MATCH_RETENTION_DAYS`, default `90`) is a **GC for pairings that stopped playing** — an app deleted or aged out is never written again, so write-time pruning can never reach its rows. The sweep is not what bounds the table; the cap is, at ~`pairs × cap` ≈ 660 rows. Sweep deletes are capped at 5,000 rows per statement and 100k per sweep so a large backlog drains over hours rather than in one long transaction. Note all of this **bounds** the table rather than shrinking it: `DELETE` leaves freed pages for the next `INSERT`, so reclaiming the pre-retention bloat needs a one-off `VACUUM (FULL, ANALYZE) ranked_match`. The leaderboard's movement arrows read a `MOVEMENT_WINDOW_MS` = **24 h** window (`AppService.getLeaderboard`), so they are now live during a post-edit re-convergence burst and flat when the board is settled; **widening that window past the retention window would silently flatten them**.

The public top-20 is `GET /api/leaderboard` (`api/leaderboard.ts`, unauthenticated, no source) + the MCP `leaderboard` tool, rendered at the UI `/leaderboard` route (main-nav "Rankings", visible logged-out). `account.lastActiveAt` (bumped, throttled, in `middleware/auth.ts`) feeds the owner-activity eligibility gate.

### SEO (public pages)

The UI is a client-rendered SPA, so the server injects per-page SEO metadata into the shell for the **public** routes (homepage, docs, lessons, examples, rankings, about, mcp, classic, blog). Keep this maintained when adding or renaming public pages:

- `server/src/util/seo.ts` — `createSeoResolver` maps a path → `{title, description, canonical, ogType, publishedTime?, noindex?, jsonLd?}`. Curated `STATIC_PAGES` map for top-level pages; `/blog/:slug` reads the shared manifest (`ui/public/blog-index.json`, also imported by `ui/src/page/blogPosts.ts` — **single source of truth**, keep the JSON and that file's type in sync); `/learn/:slug` derives title/description from the lesson markdown via `describeMarkdown`. Unknown/soft-404 routes and not-yet-published (future-dated) blog posts get `noindex`. `renderHeadTags` renders the `<title>/description/canonical/OG/Twitter/JSON-LD` block.
- `server/src/index.ts` — the **SPA fallback** replaces the `<!--SEO:start-->…<!--SEO:end-->` region in `ui/index.html` with the per-page tags (GET navigations only; the shell is read once and cached). A dynamic **`/sitemap.xml`** route (`util/sitemap.ts`) lists static routes + lessons + **published** blog posts. `express.static` sets **`X-Robots-Tag: noindex`** on `*.md` and `blog-index.json` so the raw sources don't compete with the canonical pages.
- `ui/index.html` holds the site-level default tags inside the SEO region (used in dev and as fallback); `ui/public/robots.txt` references the sitemap; `ui/public/og-card.png` (1200×630) is the social share image; `ui/public/manifest.json` is the PWA manifest. **When adding a new public page**, add it to `STATIC_PAGES` and `STATIC_ROUTES` (sitemap). Canonical/OG URLs use `PUBLIC_ORIGIN` (default `https://robocodejs.com`). Coverage: `server/test/seo.test.ts`.

**The SPA fallback must never answer a subresource** (`util/staticAssets.ts`, `isSubresourceRequest`). It serves the HTML shell for anything unmatched, which is correct for a navigation but catastrophic for a build asset: every deploy re-hashes the chunk filenames (`emptyOutDir`), so a browser still holding the previous build's HTML — a tab open across the deploy, or a load that straddled the Immutable swap while both instances were in the load balancer — requests chunks that no longer exist. Answering those with `index.html` and a `200` makes the browser execute HTML as JavaScript; it fails the module MIME check, the `React.lazy` import rejects, and with no error boundary React unmounts the whole tree to a **blank page**. So `/assets/*` and any path with a subresource extension get a real `404` (logged as `event="asset.missing"` — a spike means clients stuck on an old build), and the UI's `ChunkErrorBoundary` (`ui/src/components/chunkErrorBoundary.tsx`, wrapping the lazy `<Suspense>`) catches the rejected import and reloads **once** into the current build, guarded by a `sessionStorage` cooldown so a genuinely broken build can't loop. Every client route is extension-free, which is what makes the extension test safe — **keep it that way when adding routes**. Cache headers follow from the same split: hashed assets are `immutable, max-age=1y` (the hash is the cache key), the shell is `no-cache` (its name is stable while its contents carry the current hashes). Coverage: `server/test/staticAssets.test.ts`, `ui/test/chunkErrorBoundary.test.ts`.

### Multiple instances (GitHub #444)

Arena state lives in one process's memory, but production runs more than one instance whenever an Immutable deploy overlaps old and new (and on any ASG scale-out), so #444 gives each user a **home** instance and forwards their requests there. **Leases (phase 1):** `services/HomeService.ts` keeps a `user_home` lease row per user with arenas loaded — instance id + address from IMDSv2 in production (`util/instance.ts`; synthetic `local-<host>-<pid>` and loopback elsewhere — but a production IMDS failure falls back to the machine's private IPv4, **never loopback**, since another instance forwarding to `127.0.0.1` would be calling itself), 30 s expiry, `epoch` bumped on takeover. `EnvironmentService.get()` claims the owner's home when it builds an arena; `reconcileHomes` on the 10 s GC interval renews held leases, releases users whose last arena was collected, and **disposes the local arenas of a user whose home another instance took** (their requests now go there; `Environment.dispose` emits `disposed`, which ends every SSE stream on the arena so the browser's EventSource reconnects through the new home); graceful shutdown calls `releaseAll()` before `server.close` so the replacement instance can claim at once. A lease problem never stops an arena being served — `claim` never throws, and a database error during renew keeps every lease and reports nothing lost (no other instance can claim without the database either). `/health` reports `homeUsers`, `leaseTakeovers`, `leaseConflicts` (episodes where another instance already held a user this one serves — counted and logged **once per episode**, not per 10 s pass; with forwarding this should only come from paths that aren't forwarded yet, i.e. MCP until phase 4), `conflictedUsers` (such users right now) and `leasesLost`; `reconcile` takes the owner set as a **function**, re-read after its releases, so a user who comes back while a release is in flight is re-claimed in the same pass; the matching log events are `home.conflict`/`home.takeover`/`home.lost`/`home.error`. In the conditional upsert, `epoch` is assigned **before** `instance_id` on purpose: pg-mem applies `SET` in sequence (Postgres doesn't), so the other order never bumps the epoch under test.

**Forwarding (phase 3, `middleware/forward.ts`):** `forwardToHome` resolves a **routing key** from the path alone — `/api/user/:userId/<anything>` → that user, `/api/arena/:arenaId/…` → the arena's owner (looked up once, cached for the process: ownership never changes), `/api/demo/…` → `DEMO_USER_ID`; everything else (incl. `/api/user/:userId` itself, `/api/mcp` until phase 4, leaderboard, session, static) is served wherever it lands. `HomeService.resolve` answers local from memory, a remote home from a 15 s cache (a stale entry only costs one 421 retry), else **reads the lease first** and claims only when nobody holds a live one — so the common lookup is one indexed SELECT, not an upsert that locks the row. Such a lookup passes `claim(…, serving = false)`: finding another instance's lease while deciding where to forward is normal, not a conflict. `leaseQueries` in `/health` counts every query the lease layer issues. A remote home gets the request **proxied** to its `http://<private-ip>:8080`: the body is buffered (≤ 1 MB, so a retry can resend it), the response is **streamed** unbuffered so SSE gzip + `Z_SYNC_FLUSH` (#377) passes through, and a client disconnect destroys the upstream request so the home sees its viewer leave. Requests are signed (HMAC over method, URL, timestamp, edge id, client IP; ±60 s) with `INTERNAL_FORWARD_SECRET`; **no secret = never forward and never trust a marker**. On the home, `acceptForwarded` verifies the signature and sets `req.ip` to the edge's client IP (rather than trusting another proxy hop), and the IP-keyed `auth`/`api` limiters skip verified requests (`edgeOnly`) because the edge already counted them; the per-user limiters live in the routers and so count at the home. A forwarded request that reaches a non-home gets **`421`** (never re-forwarded, so no loops); the edge drops its cache entry and retries once. A home that can't be reached: the edge claims (succeeds only if the lease lapsed) and serves a body-less request locally; otherwise `503 Retry-After: 5`. Order in `index.ts` is load-bearing: `acceptForwarded` → IP limiters → `forwardToHome` → body parsers. Metrics: `forwardedRequests`, `forwardFailures`, `misdirectedRequests`.

**Changes to an app added by reference reach other instances on the arena's next restart, not live** (GitHub #444 section 5; phase 5 `LISTEN/NOTIFY` was deliberately dropped). `propagateSource` and `deleteAppEverywhere` update the arenas live on the saving instance, which is the app owner's home, so the owner's own arenas are always current. Another user's arena that holds the app by reference may be homed elsewhere: it keeps the version it loaded until its next restart, when `Environment.restart` reloads every app from the database (a deleted app is skipped because `appService.get` filters `NOT deleted`). Don't "fix" this with pub/sub without a reason. If it ever matters, the lighter route is a signed request to each affected owner's home, reusing the forwarding signature.

### Bot roster & membership

An arena's **roster** is its `ArenaMember` rows. A member can be **enabled or disabled** (`ArenaMember.enabled`): disabled = pulled from the live match (no `Process`/tanks) but kept in the roster so it can be re-enabled. Apps can be **added by reference** — another user's app id, e.g. via the `/add-app/:appId` **share link** — which links the app into the arena without ever exposing its source (only its live bots are visible). Roster/enable/add-by-reference routes live in `api/arena.ts`; the live status snapshot omits disabled members (they have no `Process`), and so does `match_summary`.

### Security & resource limits

Untrusted code + shared multi-user arenas make **access control, sandbox integrity, and resource exhaustion** the primary concerns. Hardening in place: `helmet` + CSP (`middleware/securityHeaders.ts`), rate limiting (`middleware/rateLimit.ts` — auth/compute/write/mcp/api limiters, `429` + error `E022`; the per-user `mcpRateLimit` guards `POST /api/mcp` and must sit after `mcpAuth` so it keys by user, not IP), RDS TLS **CA verification** (`db.ts` `sslConfig`), and resource caps — per-tank timers (`MAX_TIMERS_PER_TANK`, `E021`), per-user apps (`MAX_APPS_PER_USER`) and arenas (`MAX_ARENAS_PER_USER`) plus a global `MAX_TOTAL_ARENAS` ceiling, and the 8 MB isolate limit. A full OWASP Top 10 audit was completed and **all medium-and-above findings are remediated**; the engineering + product backlog is tracked in **GitHub Issues** (labels `tech-debt`, `enhancement`, `ai-mcp`).

**Accepted / deferred security risks** (all low severity, decided deliberately — don't "fix" without cause):

- **No server-side session revocation.** Logout just clears the cookie; a stolen still-valid Google id token works until its ~1 h expiry. Accepted — a revocation denylist is disproportionate for the short TTL.
- **Markdown rendering relies on CSP, not a sanitizer.** `showdown` → `html-react-parser` (`ui/src/.../markdownPage.tsx`) is unsanitized, but input is only our own static `/docs/*.md`, `html-react-parser` makes injected scripts inert, and the CSP is a backstop. Escalation path if untrusted markdown is ever rendered: add `DOMPurify.sanitize` before `parse()` (noted at the render site).
- **`showdown` ReDoS and XSS** (GHSA-rmmh-p597-ppvv, GHSA-cr32-g25g-vxjj metadata-title XSS, GHSA-22g5-r2x5-97cx table-header-id XSS — all moderate, no fix available): accepted for the same reason — trusted static input only. If untrusted markdown is ever rendered, take the DOMPurify escalation path above **before** shipping it.
- **The audit allowlist is empty.** `scripts/audit-check.cjs` accepts named GHSA ids so a non-applicable/unfixable advisory can be tolerated without silencing the whole gate — that's why the gate is a script rather than a bare `npm audit --audit-level=high`. Every high/critical advisory is currently either fixed or absent from the tree. When adding an entry, justify it here too; when an accepted advisory gains a fix, upgrade and remove the entry. Its last entry, the `braces` stack-exhaustion DoS (GHSA-vfj7-8cjw-p6xm, via `nodemon → chokidar 3`, no fix upstream), was retired by **removing nodemon** (GitHub #413): `npm run dev` now uses Node's built-in watchers (`tsc --watch` + `node --watch`, run in parallel by `run-p`), so `braces` is no longer in the tree at all.
- **Token entropy uses `randomUUID()`.** OAuth codes/access/refresh tokens are ~122-bit UUIDv4, stored only as sha256 hashes (`services/OAuthService.ts` via `util/hash.ts`). Adequate; `crypto.randomBytes(32)` would be the purist upgrade.
- **Lazy DDL startup robustness.** `CREATE TABLE IF NOT EXISTS` promises fire at import time without `await`/`.catch` (e.g. `AppService.ts`) — a startup race, not a vuln. Would be tidied by the DB-migrations task (GitHub issue #142).
- **`isolated-vm` ⇄ Node major coupling** (6.x needs Node ≥22; 7.x needs ≥26): move both majors together on any runtime bump.

### Services & types

`server/src/services/*Service.ts` are singleton data-access objects over Postgres (User, App, Arena, ArenaMember, Identity, Demo) plus the in-memory `EnvironmentService`. `server/src/types/*` hold both domain classes (`Tank`, `Arena`, `Environment`, `Process`) and plain DTOs; `ui/src/types/*` mirror the wire DTOs. `ErrorCodes.ts` defines the `E0xx` codes surfaced in bot logs.

## Conventions

- **Make each change in its own git worktree.** The maintainer prefers every change be developed in a dedicated worktree (under `.claude/worktrees/`) on its own branch off `main`, rather than committing on a shared checkout — so multiple in-flight changes don't conflict. One worktree/branch per task/PR; open a PR rather than committing to `main` directly.
- A user can own multiple arenas. Each arena action route is registered at **two paths sharing one handler** (`api/arena.ts`, via the `dual()` helper): `/api/user/:userId/arena/...` resolves the user's **default arena** (first by creation time, lazily created if none) and is what the UI uses, while `/api/user/:userId/arenas/:arenaId/...` addresses a **specific arena** and is intended for tooling. The `resolveArena` middleware (`middleware/resource.ts`) picks the right one and enforces that an `:arenaId` belongs to `:userId`. The collection lives at `/api/user/:userId/arenas` (GET list, POST create — capped at `MAX_ARENAS_PER_USER`), with `DELETE .../arenas/:arenaId` to tear one down. Keep the UI single-arena: add arena management to tooling against `/arenas`, not the UI.
- Server logging uses the structured **pino** logger in `server/src/util/logger.ts` (pretty in dev, JSON in prod, silent in test, `LOG_LEVEL`-tunable) — use it, not `console.log`. This is separate from the per-tank bot `console` output (browser-bunyan → SSE). Fault/security conditions are logged with a stable `event` field via `LogEvent`/`logBotFault` (e.g. `bot.fault` with `timedOut`, `auth.forbidden`); see the server README "Logging & monitoring".
- Code style is enforced by prettier + eslint with `--fix`; one root `.prettierrc.json` governs the whole repo, eslint is per-package (each resolves its own plugins). Run the package `lint` script rather than hand-formatting. A **Husky pre-commit hook** (root `.husky/pre-commit` → `lint-staged`, configured in `.lintstagedrc.cjs`) runs `prettier --write` on staged files, so commits are auto-formatted; it's activated by the root `prepare` script on `npm install`. Generated files are excluded via `.prettierignore` (e.g. `ui/public/docs/ts`, the generated `robocode.d.ts`).
- The hook **applies** formatting; the **`format` CI job gates it** (`prettier --check` over `git ls-files`, failing the build). The hook alone isn't enough — it's skipped by `git commit --no-verify` and absent until someone runs a root `npm install`. The job runs at the **root** on purpose: the package `lint` scripts only cover `src test`, so nothing else checks top-level files or `ui/public/**` — which is exactly where the only drift ever found (`CLAUDE.md`, two blog posts) had accumulated. Note CI must never call `npm run lint`, which is `--write`/`--fix` and would mutate the checkout while still exiting 0.
